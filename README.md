# RPX XUI Core Library

Shared EXUI library consolidating capabilities from CommonLib, CCD Toolkit, Translation and Node Lib behind explicit package entry points: browser features stay selective, with server code in Node-only entries.

**Status:** private Angular 20 and Node package with active migrations across CommonLib UI/services, CCD Toolkit case capabilities, Translation and Node authentication/session support. The local gallery and package checks exercise built output, but they do not establish full source-library parity, application cutover, supported release compatibility or production bundle savings. Publication remains disabled with `private: true` in both workspace and staged package.

## Scope

| Source repository | Intended responsibility |
| --- | --- |
| [rpx-xui-common-lib](https://github.com/hmcts/rpx-xui-common-lib) | Shared UI and browser support |
| [ccd-case-ui-toolkit](https://github.com/hmcts/ccd-case-ui-toolkit) | Case lists, forms and rendering |
| [rpx-xui-translation](https://github.com/hmcts/rpx-xui-translation) | Translation |
| [rpx-xui-node-lib](https://github.com/hmcts/rpx-xui-node-lib) | Server support |

Media Viewer and payment integrations remain external. The repository configuration follows common-lib; its aggregate runtime module is not the target architecture.

The `/ui/accessibility` entry provides the original CommonLib accessibility statement and selector. The diagnostic gallery at `/accessibility` exercises its application context and Welsh heading with local synthetic translations. The source statement is preserved; this gallery does not establish accessibility conformance or consumer adoption.

## Develop locally

Use Node **24.22.2** from `.nvmrc` and the checked-in Yarn release. With asdf:

```sh
core_node_path=$(asdf where nodejs "$(cat .nvmrc)")
export PATH="$core_node_path/bin:$PATH"
node --version
node scripts/core-yarn.mjs --version
node scripts/core-yarn.mjs install --immutable
node scripts/core-yarn.mjs playwright install chromium
```

With nvm, run `nvm use` instead. Confirm Node prints `v24.22.2`. `core-yarn.mjs` follows `yarnPath` from `.yarnrc.yml`; immutable install does not change the lockfile.

Angular's compiler cache uses LMDB. The workspace resolves `lmdb` and its platform binaries to 3.5.1: on macOS arm64 with Node 24.22.2, the 3.4.2 binary aborts during cache teardown before editor tests run. Keep the seven `@lmdb/*` resolutions aligned with `lmdb` when changing this workaround. It is development-tooling only and is not imported by the published Core entries.

### Run the library locally

Start the package watcher and gallery:

```sh
node scripts/core-yarn.mjs start
```

Wait for `Validation diagnostic build ready` and `http://127.0.0.1:4307`. The watcher builds Core before serving the gallery, then rebuilds after source, template or style edits. Use the gallery's synthetic examples to exercise the built package. Stop the process with Ctrl+C. Stop the gallery before browser suites that use port 4307.

```sh
node scripts/core-yarn.mjs test:all
```

This builds and lints Core, runs the component and Node contracts, checks the packed package, runs the browser suites and compares reports with the required test inventory. It includes editor tests against source and a freshly packed artifact. The CI `build` job uses the same gate. The full run deletes previous `test-results/` and uses shared local ports; preserve reports you need and do not run another browser suite in the same checkout at the same time.

## Package layout and initial build cohort

Official ng-packagr emits a structural metadata-only primary entry point plus focused secondary entries such as `forms/validation`, `i18n`, `browser/user-agent`, `ui/contact-details`, `ui/loading-spinner`, `ui/loading-state`, `ui/due-date`, `ui/accessibility`, `ui/session-dialog`, `ui/banner`, `ui/form-label`, `ui/hmcts-error-summary`, `ui/hmcts-sub-navigation`, `ui/ccd-pagination`, `ui/case-list`, `util/json`, `case/models`, `case/reference`, `case/sharing`, `case/logging` and `case/session-guard`. The root primary exists because Angular Package Format requires it; its source exports no runtime capability and imports no secondary implementation. It must never become an aggregate root module. Native packaging emits physical `forms/validation/index.d.ts` declarations for legacy consumers and an independent validation FESM. No primary-to-secondary export rewriting or old `/validation` alias is used.

The APF build contract is Angular/compiler-cli **20.3.35**, ng-packagr **20.3.2**, TypeScript **5.9.3**, and Node **24.22.2**, with the gallery using Angular CLI/build **20.3.42** and framework **20.3.35**. The packed validation entry is also built with Angular **20.3.31** and RxJS **7.8.2**, matching the current application cohort used by the package check. These exercised versions do not promise broad version support; further supported cohorts need their own installed fixtures. The gallery keeps strict TypeScript/template checks. The library build retains `strict: false`, `noImplicitAny: true`, `skipLibCheck: false` for the remaining translation migration. Lint separately checks validation source under full strictness using `projects/core-lib/forms/tsconfig.strict.json`; Node source, consumer fixtures and gallery templates are also strict. Translation class-initialisation diagnostics remain an explicit migration item.

The validator is derived from [rpx-xui-common-lib published revision f23288743831ef13a55b4348f757db74c1a189c8](https://github.com/hmcts/rpx-xui-common-lib/blob/f23288743831ef13a55b4348f757db74c1a189c8/projects/exui-common-lib/src/lib/gov-ui/validators/checkboxes-be-checked.validator.ts). The original source SHA-256 is `095a8cb877b637406efcb175b2d73775a199104c26e2142b307d18f7d94673c3`; core now narrows the generic Angular control at runtime and rejects a non-FormGroup with a clear error so its callback satisfies strict function variance. Its original MIT licence and 2019 Crown Copyright notice are retained at `forms/validation/LICENCE` in the distribution, alongside the core licence. The preserved behavior counts boolean `true` only, defaults to minimum one and returns `requireOneCheckboxToBeChecked`. Existing AO/common/MO source packages and production authority are unchanged.

The same entry now exports CommonLib's `dateValidator` and `radioGroupValidator` from that revision. `radioGroupValidator` retains its `{ isRadioGroupInvalid: true }` error when any child is invalid and returns `null` for an empty group. `dateValidator` retains the `{ dateIsInvalid: true }` key and requires `day`, `month` and `year` controls. **Intentional compatibility correction:** CommonLib subtracts one from both day and year before constructing a JavaScript `Date`, which can let an impossible date such as 31 February pass. Core validates the entered calendar date directly, including leap years, and rejects blank or invalid parts. The copied Manage Org validator has the same defect and is not changed in this library PR; consumer cutover needs an explicit regression check. Core's `ui/gov-date` component validator remains separate because it has a different error key and supports optional empty dates.


The focused UI entries preserve the common library contact-details, loading-spinner, due-date, session-dialog, banner and form-label selectors, models and translation labels. The session-dialog adds a translated accessible name and uses native modal focus isolation, restores the previous connected focus target on teardown, and retains explicit stay-signed-in or sign-out actions when Escape is pressed. The spinner exposes changing text through a status region and respects reduced motion. The gallery routes `/contact`, `/spinner`, `/due-date`, `/session-dialog` and `/primitives` exercise component states and translations. Their original 2019 Crown Copyright licences are included in both the built and installed package.

`ui/case-list` exposes the Toolkit 7.4.27 `CaseListModule`, `CaseListComponent`, `TableConfig`, `TableColumnConfig` and `DateTimeFormatUtils` as a selective entry. Its dependency on `ui/ccd-pagination` preserves the numbered `ccd-pagination` page events; `ui/pagination` and `ui/hmcts-pagination` have different contracts and are not substituted. `browser/user-agent` contains the same `BrowserService` class used by the list and editor search-result/text-area paths. The editor imports those shared entries, so it does not keep duplicate component, paginator or service classes. Packed graph checks prove a case-list-only import does not load `case/editor-source` or the Node/server, Media Viewer or payment entries.

The `ui/ccd-pagination` tests exercise the actual Toolkit component independently of the generic and HMCTS paginators: public input defaults and string boolean coercion, keyboard page changes, default and custom labels, one-page auto-hide, page-bounds correction after results shrink, accessibility checks and installed-package behavior. Its `navigationLabel` input defaults to the Toolkit-compatible `Pagination`; set a distinct value when a page renders multiple CCD paginators so their navigation landmarks remain distinguishable. These Core checks do not prove a consumer has switched from Toolkit or establish a production bundle reduction.

The migration preserves Toolkit table, selection and pagination inputs and outputs. It intentionally corrects inherited edges with focused tests: browser predicates are called rather than treated as truthy method references; an empty list is not marked fully selected; an absent `cases` input is normalized to an empty array; selection checkboxes receive explicit accessible names and no longer use colliding empty-label ID references. The accessible name translates only the fixed `Select case` phrase and appends the case identifier locally; this avoids adding the ID through that accessibility label. Legacy text and link cell values continue through `rpxTranslate`, so a consumer that displays an identifier in a text or link column may still include it in translation requests. Changing that existing cell behavior requires a separate consumer compatibility decision. Select-all still applies to the full `cases` input, including entries on other pages. These local synthetic journeys do not establish consumer adoption or assistive-technology acceptance. The original Toolkit source commit is `007d1175b81933bba9685fe26078035e4d55bc23`; the gallery route is `/case-list`.

`case/models` owns the shared Draft and CaseDetails classes; `case/reference` imports that same Draft class and preserves the toolkit case-reference pipe's formatting, draft detection and link handling. The `/case-reference` gallery and installed-package checks cover these contracts. Both case entries retain the original toolkit 2017 HMCTS licence. These slices do not establish application adoption or the complete case renderer.

`case/session-guard` is the small browser route guard for malformed session data. It uses the canonical `SessionStorageService` and shared logger entries. Editor internals reuse those same class identities through internal compatibility re-exports, while `case/notifier` retains its public logger re-export; the guard itself is public only from `case/session-guard`. Consumers own the `/session-error` route and can override it with `SessionErrorRoute`; the error page is loaded by the application's route, so the guard does not eagerly import it. Unit tests verify absent and valid data allow navigation, malformed and JSON `null` redirect, the configured logger and route are honored, and class identity remains shared. Packed browser tests verify absent and valid routes, the malformed-data redirect, lazy error-page loading and that no stored-value snippet reaches browser diagnostics.

`util/json` exposes the Toolkit `safeJsonParse` function through a small entry, and `case/notifier` keeps its existing re-export for compatibility. Both paths use one implementation. Core intentionally logs only the parse error name, whereas Toolkit logs the full exception object; JavaScript syntax errors can include malformed input in their message. The fallback behavior and valid JSON values are preserved, and a sentinel test proves the malformed value is not logged. Web App still imports the Toolkit function; switching those callers is a separate consumer adoption change.

### Node migration behaviour changes

These are intentional, observable differences from `rpx-xui-node-lib` master at source revision `722b6284da957dbf4eebde0b49d36574d9664e3e`; Webapp consumer behavior was checked at `1a986f4dc87e6ea4598e30c042bf2b3072122b75`. Core does not claim identical auth/session diagnostics or failure payloads. Node Lib PR [#368](https://github.com/hmcts/rpx-xui-node-lib/pull/368) remains open at `de24e6aaf6c0ac3990581e4f07e95b41961cd088`; its readiness work is still a candidate, not the merged baseline. These differences require consumer review before adoption:

| Area | Core behaviour | Difference and consumer impact |
| --- | --- | --- |
| Authentication/session logging | Logs lifecycle events, HTTP methods/statuses and safe error names. It omits credentials, tokens, state values, callback/provider URLs and query strings, user identifiers/profiles, OIDC metadata, raw errors and Redis client objects. | Log searches and alerts that parse these values or old message text must be updated. Where applicable, original errors still flow through Express `next(error)`; downstream handlers may apply their own logging. Deeper diagnosis may need existing host request/provider diagnostics; this change does not add correlation IDs. |
| Authentication failure payload | `AUTHENTICATE_FAILURE` receives a generic timeout or service-error message instead of the raw provider error and URL. | This is consumer-visible: the current Webapp handler logs and sends `res.locals.message` to App Insights (source `1a986f4dc87e6ea4598e30c042bf2b3072122b75`). Expect different telemetry grouping and less provider detail; consumers must not depend on the old raw payload. |
| OIDC startup discovery failure | Discovery has a 15-second request timeout and retries once after 250 ms. If both attempts fail, strategy readiness stays failed; `XuiNode` forwards the error through Express and does not enter the protected router. Core retry diagnostics record only the error type. | The retry can recover a short provider outage during startup. After the bounded retry is exhausted, this process does not recover authentication automatically; operators must restart it after IdAM discovery is available. The final error still reaches host Express error handling, whose logging policy remains consumer-owned. |
| Logout when IdAM is unavailable | Access/refresh token revocation is best effort, bounded to five seconds per token, and local Passport/session cleanup still runs. | Logout no longer leaves a live local session or returns the old revocation-failure redirect just because IdAM is unavailable. Consumers must treat remote revocation as best effort; local session destruction is the logout guarantee. |
| CSRF token source | Unsafe requests must submit the token in a request body or supported CSRF/XSRF header. The readable `XSRF-TOKEN` cookie is issued for clients to copy into a header, but the server does not accept that cookie itself or a query parameter as proof. | Query-string and cookie-only CSRF submissions now fail. Angular's configured `X-XSRF-TOKEN` header remains supported; consumers that use query tokens must move them to a body field or header. |
| OIDC refresh and recovery | Login/logout routes bypass keep-alive refresh; a successful refresh response may omit rotated refresh or ID tokens without deleting the existing values, while a response without an access token fails closed and leaves the current session token set intact. | Login and logout remain available when IdAM introspection/refresh fails. Providers that omit refresh/ID token fields retain the existing session values; malformed refresh responses are sent to Express error handling rather than leaving Passport authenticated with missing tokens. |
| Password-grant form body | `URLSearchParams` encodes every field. | The wire representation changes for reserved characters in username, scope, client ID and client secret; decoded values are preserved and those fields are now safely encoded. |
| Authentication startup | `XuiNode` waits for middleware exposing `waitUntilReady()` before dispatching requests to the configured router. | Node Lib master does not gate dispatch on setup. Open PR #368 adds a setup gate, but its strategy initializer still runs in an unawaited async task. Core also awaits strategy readiness and forwards setup failures through Express `next(error)`, avoiding requests through partially initialized middleware. Custom async middleware may expose the same readiness hook. |
| Redis event dispatch | Dispatch checks for listeners on the event being emitted. | `REDIS_CLIENT_ERROR` listeners now receive errors even when no `REDIS_CLIENT_READY` listener is registered; the event name and emitted error object are unchanged. |
| Logger namespace cache | Cache keys use the complete emitted namespace. | Legacy loggers sharing a final segment could reuse the first prefix and its `DEBUG` filter. Core keeps those prefixes distinct while retaining identical-name reuse, delimiter behavior and late console instrumentation. Check namespace-based diagnostics during cutover; message arguments are unchanged. |
| Dependency installation footprint | Node server dependencies are declared by the Core package; Angular peers remain optional. Runtime imports stay behind explicit Node-only entry points. | Package managers still install and audit the Node dependency graph for browser-only consumers. Selective graph checks prove the chosen browser entry does not load Node server code; they do not reduce install or lockfile size. Avoiding that install cost would require a second published package or consumer-supplied optional peers, changing the one-package/self-contained-Node tradeoff. |

Treat these as migration contract changes or explicit package tradeoffs, not silent cleanup. Validate log/telemetry consumers and startup/error handling during each application's cutover. The Node tests cover redaction, generic failure messages, form encoding, readiness and Redis event routing; package checks prove Node-only resolution and browser-entry isolation, not reduced dependency installation.

`yarn build` compiles the Node tree as CommonJS alongside the Angular output. The tarball includes its own `node/package.json` marker and declarations. `yarn test:node` runs the Node utility contracts, migrated server Jest suite and build-watch regression; the aggregate gate also requires their native TAP report. Packed-package checks exercise `/node`, `/node/server`, `/node/server/auth` and `/node/server/session` in isolated consumers, verify strict declarations and runtime dependency resolution, and reject browser imports. Browser/gallery watch does not watch Node source; run `yarn build` after Node edits.

The full gate records the migrated Node server suite in native Jest JSON at `test-results/node-server.json`, bound to the source snapshot and run through its own `nodeServerUnit` receipt. All 177 current cases are required by stable spec-path/full-name identity and grouped into authentication strategy, login-handler failure completion, OIDC, token refresh, OAuth2, service authentication, application middleware, file sessions, Redis sessions, content security policy, local HTTP session behavior and logger namespace isolation in the feature matrix. Missing cases, skipped/todo/expected-failure outcomes, retries, zero-expectation cases, interruption, runtime errors, inconsistent totals and changed report bytes cannot satisfy this gate. Every executed outcome in every supervised lane must be registered in `tests/contracts.json` and `tests/feature-evidence-map.json`. ### Node content security policy

`@hmcts/rpx-xui-core-lib/node/server/security` provides `csp`, `getContentSecurityPolicy`, `SECURITY_POLICY` and `CspOptions` from Node Lib source `722b6284da957dbf4eebde0b49d36574d9664e3e`. Importing this entry requires the optional `helmet@^8.1.0` peer at runtime. Peer metadata applies to the whole package: a consumer already providing Helmet must satisfy this range even when it imports another entry. Runtime isolation does not isolate package-manager peer constraints. The maintained package gate tests Helmet 8.1.0, 8.2.0 and 8.3.0 with strict declarations, the three frozen app configuration shapes, local HTTP, browser enforcement and dependency audits. The development/main installed fixture and inspected app locks select 8.3.0. The range replaces the legacy library's incompatible Helmet 7 peer declaration; future releases and real app adoption still require validation. Other Node and browser entries do not import Helmet. For logger-only consumers, import `getLogger` and `XuiLogger` from `/node/server/logging`: installed runtime and bundle guards keep authentication, sessions, security and their dependencies out of that entry. The broader `/node/server` convenience entry exposes the same logger implementation.

The middleware keeps the source policy values, per-request nonce, environment/default/explicit-empty-array behavior, array concatenation order and duplicates. `CSP_REPORT_ONLY` still takes effect per request and generated `useDefaults`/`reportOnly` values retain their precedence over the supplied default policy. The injected `getContentSecurityPolicy` helper receives the existing policy object by reference. The broad non-nullish `defaultCsp` option remains accepted; Helmet validates recognized runtime fields.

Three differences are intentional and covered by tests: the CSP-specific merge preserves valid custom iterable directive values instead of the old generic merger corrupting them; it snapshots own root options and directive values once per request when combining generated arrays, so inherited policy values cannot shadow nonce-bearing directives; and an own `__proto__` directive reaches Helmet's invalid-name rejection instead of being silently discarded. It does not reject the valid directive-name tokens `constructor` or `prototype`. There is no runtime deepmerge/fork dependency. These changes do not tighten the allow lists, normalize source strings, remove duplicates or change the existing style-attribute policy. The full gate covers native HTTP headers, real browser enforcement/report-only behavior, packed app option shapes and controlled nonce/header/merge faults. The frozen app fixtures redirect imports and configuration to synthetic local values; they do not establish whole-application cutover or deployment acceptance.

The local HTTP session checks exercise the real Express/express-session middleware with an in-memory store: signed-cookie reuse, fresh and tampered-cookie isolation, uninitialized-session behavior, expiry/HttpOnly/secure flags, and a store error reaching the application handler before the protected route. Controlled wrong-cookie, wrong-store and save-uninitialized faults fail those checks and restoration passes. This proves the middleware contract with that store; it does not establish Redis protocol, deployed TLS or proxy configuration acceptance.

## Translation preparation

`@hmcts/rpx-xui-core-lib/i18n` owns the published Translation 1.2.18 implementation (`c64cbe88f3f84a2d32ca9006f75c48a71a6dfc3b`), including its service/config classes, pipe, module and IndexedDB cache, with the later language-switch fix from source master `ca94b533c796a6f75c56c27dbf13a50b6feed0ed` and core fixes for overlapping request batches, arbitrary phrase dictionary keys, provider-owned work teardown, validated response/locale boundaries and cache-failure recovery. The MIT licence is preserved. Core runtime dependencies are Dexie 4.4.7 and Luxon 2.5.2. Dexie is aligned with the resolved published legacy cohort; the historical 4.4.4 alias is used only for cache migration tests. Luxon retains the published dependency contract rather than adopting the source workspace's Luxon 3 build dependency.

`yarn test:i18n` runs all 86 translation contracts in Angular 20's experimental Vitest Chromium runner with zoneless timing, then checks the separate browser host with Playwright. The native Vitest receipt at `test-results/i18n/vitest.json` records the installed runner version, every test outcome, unhandled errors and console diagnostics. The lane requires the exact 86-name inventory and removes any old receipt before running. Known test-scoped cache-failure diagnostics are accepted; unexpected or unattributed browser console errors fail the evidence gate. Playwright JUnit at `test-results/i18n/driver-junit.xml` reports the one host driver, not the 86 component contracts. `yarn test:browser` also exercises the lazily loaded [translation gallery](http://127.0.0.1:4307/translation): locale persistence, real HTTP, IndexedDB cache reuse after reload, HTTP-error fallback, and a delayed response after switching language. The gallery uses built `/i18n` output; validation startup does not import it eagerly.

New `tests/i18n/**/*.spec.ts` files are discovered by the Vitest target. The independent contract inventory requires every existing outcome exactly once; update it when adding or intentionally changing a contract. Angular's unit-test builder is experimental, so its browser-runner behavior remains an adoption risk until the complete CI lane is green.
For values that must remain literal, pass a separate literal map as the third argument to `getTranslationWithReplacements$`, for example `service.getTranslationWithReplacements$('Hello %NAME%', {}, { NAME: name })`. In templates use `phrase | rpxTranslate: null: undefined: { NAME: name }`. Literal values are inserted without translation or translation-cache storage and retain their exact whitespace. Existing string replacements retain their translation behaviour. A key cannot appear in both maps. Callers must still avoid passing personal data as the phrase itself or as a translatable replacement; changing this API does not automatically migrate existing consumers.

`yarn test:cache-upgrade` first rejects a controlled baseline source mismatch, then checks sequential cache reuse between published legacy translation, a historical Dexie 4.4.4 core baseline and the installed Dexie 4.4.7 candidate. It covers both directions, expired-row refresh and literal-value privacy after reload. The historical baseline must have the same core source as the candidate; receipts verify source and bundled versions. Run `yarn build` and `yarn test:package` first: the lane verifies and uses the tarball produced by that package check. It uses separate browser documents at the same origin and path; no-refetch observation is bounded to 75 ms after cached rendering. Reports and the package/source-map receipt are under `test-results/cache-upgrade-*`. This does not establish simultaneous provider identity, deployed application behaviour or release compatibility.

Translation input is a data boundary: send only approved static UI text to the configured service. Existing string replacements are themselves translated; do not assume they stay local. User and case values passed directly as phrases can also reach HTTP and persistent IndexedDB. Consumer owners must classify these values, choose an approved endpoint and decide cache lifetime before adoption. Browser storage is an optional cache, not confidential storage. Validated malformed responses fall back without caching; storage failures preserve usable output and log only fixed failure categories.

### Odhín browser reports

The browser and installed-package/cache lanes use common-lib’s patched Odhín 1.1.8 reporter and responsive presentation. Their reports are `test-results/odhin/browser/index.html` and `test-results/odhin/cache-upgrade/index.html`. Reporter provenance is recorded in [tests/reporters/PROVENANCE.md](tests/reporters/PROVENANCE.md).

The browser report places required browser-contract outcomes on the main Dashboard. Its test-results table starts at 100 rows per page (with 10, 25 and 50 still available); a previously saved smaller page size does not override that default.

The existing native HTML, JSON and JUnit reports remain enabled by default. `PLAYWRIGHT_DEFAULT_REPORTER` changes the terminal reporter (`list` locally, `dot` in CI); `PLAYWRIGHT_REPORTERS=list,odhin` selects an explicit set for a standalone run. ## Architecture contract

One installed package must not become one eagerly loaded application bundle. The planned package uses real capability entry points, with no root aggregate module. Small startup/UI/validation consumers must not retain the case renderer or Node implementation. Applications own route-level dynamic loading; entry points alone do not make imports lazy. Installing one package still installs its declared dependency set.

Candidate boundaries include session support, case configuration, validation, focused UI capabilities, case lists, the coupled case renderer, translation and Node services. Names and granularity remain subject to real dependency graphs and packed-output evidence. Do not add placeholder public APIs to reserve them.

Before bulk migration:

1. Confirm supported consumers, framework versions and the complete dependency contract.
2. Prove browser/server isolation and declaration resolution using the actual packed artifact, including the Node CommonJS marker.
3. Prove canonical translation ownership and the legacy facade with compatible external Media Viewer/payment releases and a representative case path.
4. Measure small-consumer, startup-versus-renderer and list-only loading with the consumers' real builders.

Broader supported Angular cohorts and the complete future manifest remain design/compatibility gates. This foundation proves only its concrete initial APF dependency graph; publishing credentials and release automation remain absent. Package release must eventually publish the exact tested tarball without rebuilding it.

### Hearing lookups

The migrated case-confirmation component uses an empty `FormGroup`, where Toolkit used a `FormControl` for its public `formGroup` property. Angular's strict template compiler rejects the old control at `[formGroup]`; rendered submission is covered locally. This public type and behavior difference is intentional and still requires consumer review before adoption.

The event-history API retains Toolkit's string-typed emitter and selected-event properties. Its template uses a localized Angular type escape because the source event model permits numeric IDs; the runtime value is forwarded unchanged. Consumers must not infer runtime string normalization from the legacy TypeScript annotation.

Editor link navigation retains Toolkit's empty-string `queryParams` fallback when no query is present. Angular's current router types require a localized TypeScript cast for that legacy runtime value; local tests confirm both the exact argument and its URL behavior.

The case notifier and editor use the existing Core `SessionStorageService` token rather than a second Toolkit copy. Normal one-argument reads retain Toolkit behavior. Core also supports `getItem(key, true)` to remove the item after reading; Toolkit's JavaScript implementation ignored an extra second argument, so callers relying on that unsupported usage must review the change.

The case notifier reuses Core's existing `CaseDetails` and `Draft` classes. Their field and draft helper definitions match the migrated Toolkit versions; class identity is now shared across these Core entry points, which changes `instanceof` results compared with two independent copies.

Query field resolution is reset for each query-writing attempt. If the current case cannot resolve an editable query field, Core clears the prior field and collection state and does not create a raise-query or response payload. This intentionally prevents a failed lookup from reusing data cached for a different case; consumer query journeys still require integration verification.

The editor's pipe module reuses Core's `CaseReferencePipe` and `CaseReferenceModule`. Formatting behavior is unchanged for the tested reference and draft examples; class identity is now shared instead of duplicated.

The editor's form module reuses the existing Core `DateInputComponent` and `DateInputModule` instead of a second component. The shared class identity is observable to consumers and remains subject to adoption review.

`yarn test:editor:translation-compatibility` is a strict adoption diagnostic for the installed legacy translation package. It currently fails against `rpx-xui-translation` 1.2.18 because its module and service are separate from Core's; it is intentionally separate from the Core development suite while the translation facade and consumer release path are unresolved. The packed preview facade is tested separately by `yarn test:package` and is not a released replacement.

### Remaining GOV.UK controls (local migration candidate)

Focused entries `ui/gov-radio`, `ui/gov-radios`, `ui/gov-checkboxes`, `ui/gov-checkbox`, `ui/gov-textarea` and `ui/gov-file-upload` preserve CommonLib selectors and input contracts. `ui/gov-checkbox` is independently importable for Manage Org permission forms; `ui/invitation` reexports the same checkbox class and module so existing invitation imports keep their identity. The shared wrapper, fieldset and host-removal directive live in `ui/form-group`; invitation reexports the same wrapper/fieldset classes. The textarea intentionally fixes CommonLib's hardcoded `more-detail-hint` ID: hints now use each configured control ID and render only when present. This corrects missing described-by targets and duplicate hint IDs when several textareas appear together. Consumer markup/CSS and assistive-technology acceptance remain required. These entries are being validated locally and are not yet a completed consumer cutover.

The new textarea, file-upload and checkbox controls also explicitly expose `aria-invalid` from the parent error state and omit error description IDs when no error messages render. CommonLib showed an error class without the invalid attribute and could reference a missing error node. These are intentional accessibility corrections; the controls still use parent-owned error state rather than introducing new validators or changing submitted values.

Run the focused native controls checks with `node --test tests/form-primitives/*.test.mjs` after a build. ### CommonLib HMCTS shell: main wrapper and primary navigation

The CommonLib `xuilib-hmcts-main-wrapper` and `xuilib-hmcts-primary-navigation` components are exposed as separate `ui/hmcts-main-wrapper` and `ui/hmcts-primary-navigation` entries. Their source is CommonLib commit `f8566da8a53bff16177deeef824a0642a631285c`; both retain their original Crown Copyright licence. The wrapper depends only on Core's error summary, banner and translation entries; primary navigation depends on translation. Approve Org is the confirmed consumer. Neither entry imports the CommonLib aggregate module.

The public inputs, selectors, translated text, projected content, summary-error `isFromValid` spelling, and `backEvent` output are retained. The legacy `any` error-message type remains under a narrow lint exception. CommonLib declares action callbacks as returning `{}`, while Manage Org's current wrapper uses `void`; Core exposes `void` because the wrapper ignores callback results. This intentionally widens which consumer callbacks type-check, but changes the exported return type, so the package contract compiles both shapes and consumer builds must still be checked before adoption. Two keyboard-access issues are corrected: event-only Back navigation now renders a real button, and wrapper action callbacks render real buttons instead of anchors without `href`. With `backLink` set, Back remains a router link and still emits `backEvent`. An empty or absent primary-navigation label uses the translated `Primary navigation` fallback, avoiding an empty `aria-label` and preserving an accessible name. The navigation Sass uses the public GOV.UK base module because the legacy `objects/width-container` path no longer exports its mixins in the current GOV.UK version. These intentional compatibility or build adjustments are documented for consumer review. Browser contracts cover route and event paths, validation/banner/action content, signed-in visibility, navigation state, keyboard operation and accessibility; package contracts check public declarations and isolate both entry graphs. Local synthetic-host evidence does not replace Approve Org's adoption and end-to-end acceptance.
