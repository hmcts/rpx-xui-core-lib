# RPX XUI Core Library

Repository foundation for consolidating four EXUI libraries into one npm package, with focused browser entry points and a separate Node entry.

**Status:** private Angular 20 and Node package foundation. Migrated capabilities include the checkbox validator behind `@hmcts/rpx-xui-core-lib/forms/validation` and the Node-only auth, session and `XuiNode` runtime. The private gallery exercises built UI output. This is not application adoption, a supported consolidation release, or complete package-feasibility evidence. Library package publication remains disabled with `private: true` in both workspace and staged package.

## Scope

| Source repository | Intended responsibility |
| --- | --- |
| [rpx-xui-common-lib](https://github.com/hmcts/rpx-xui-common-lib) | Shared UI and browser support |
| [ccd-case-ui-toolkit](https://github.com/hmcts/ccd-case-ui-toolkit) | Case lists, forms and rendering |
| [rpx-xui-translation](https://github.com/hmcts/rpx-xui-translation) | Translation |
| [rpx-xui-node-lib](https://github.com/hmcts/rpx-xui-node-lib) | Server support |

Media Viewer and payment integrations remain external. The repository configuration follows common-lib; its aggregate runtime module is not the target architecture.

The `/ui/accessibility` entry provides the original CommonLib accessibility statement and selector. The diagnostic gallery at `/accessibility` exercises its application context and Welsh heading with local synthetic translations. The source statement is preserved; this gallery does not establish accessibility conformance or consumer adoption.

### Node migration behaviour changes

These are intentional, observable differences from `rpx-xui-node-lib` master at source revision `722b6284da957dbf4eebde0b49d36574d9664e3e`; Webapp consumer behavior was checked at `1a986f4dc87e6ea4598e30c042bf2b3072122b75`. Core does not claim identical auth/session diagnostics or failure payloads. Node Lib PR [#368](https://github.com/hmcts/rpx-xui-node-lib/pull/368) remains open at `de24e6aaf6c0ac3990581e4f07e95b41961cd088`; its readiness work is still a candidate, not the merged baseline. These differences require consumer review before adoption:

| Area | Core behaviour | Difference and consumer impact |
| --- | --- | --- |
| Authentication/session logging | Logs lifecycle events, HTTP methods/statuses and safe error names. It omits credentials, tokens, state values, callback/provider URLs and query strings, user identifiers/profiles, OIDC metadata, raw errors and Redis client objects. | Log searches and alerts that parse these values or old message text must be updated. Where applicable, original errors still flow through Express `next(error)`; downstream handlers may apply their own logging. Deeper diagnosis may need existing host request/provider diagnostics; this change does not add correlation IDs. |
| Authentication failure payload | `AUTHENTICATE_FAILURE` receives a generic timeout or service-error message instead of the raw provider error and URL. | This is consumer-visible: the current Webapp handler logs and sends `res.locals.message` to App Insights (source `1a986f4dc87e6ea4598e30c042bf2b3072122b75`). Expect different telemetry grouping and less provider detail; consumers must not depend on the old raw payload. |
| Password-grant form body | `URLSearchParams` encodes every field. | The wire representation changes for reserved characters in username, scope, client ID and client secret; decoded values are preserved and those fields are now safely encoded. |
| Authentication startup | `XuiNode` waits for middleware exposing `waitUntilReady()` before dispatching requests to the configured router. | Node Lib master does not gate dispatch on setup. Open PR #368 adds a setup gate, but its strategy initializer still runs in an unawaited async task. Core also awaits strategy readiness and forwards setup failures through Express `next(error)`, avoiding requests through partially initialized middleware. Custom async middleware may expose the same readiness hook. |
| Redis event dispatch | Dispatch checks for listeners on the event being emitted. | `REDIS_CLIENT_ERROR` listeners now receive errors even when no `REDIS_CLIENT_READY` listener is registered; the event name and emitted error object are unchanged. |
| Logger namespace cache | Cache keys use the complete emitted namespace. | Legacy loggers sharing a final segment could reuse the first prefix and its `DEBUG` filter. Core keeps those prefixes distinct while retaining identical-name reuse, delimiter behavior and late console instrumentation. Check namespace-based diagnostics during cutover; message arguments are unchanged. |
| Dependency installation footprint | Node server dependencies are declared by the Core package; Angular peers remain optional. Runtime imports stay behind explicit Node-only entry points. | Package managers still install and audit the Node dependency graph for browser-only consumers. Selective graph checks prove the chosen browser entry does not load Node server code; they do not reduce install or lockfile size. Avoiding that install cost would require a second published package or consumer-supplied optional peers, changing the one-package/self-contained-Node tradeoff. |

Treat these as migration contract changes or explicit package tradeoffs, not silent cleanup. Validate log/telemetry consumers and startup/error handling during each application's cutover. The Node tests cover redaction, generic failure messages, form encoding, readiness and Redis event routing; package checks prove Node-only resolution and browser-entry isolation, not reduced dependency installation.

`yarn build` compiles the Node tree as CommonJS alongside the Angular output. The tarball includes its own `node/package.json` marker and declarations. `yarn test:node` runs the Node utility contracts, migrated server Jest suite and build-watch regression; the aggregate gate also requires their native TAP report. Packed-package checks exercise `/node`, `/node/server`, `/node/server/auth` and `/node/server/session` in isolated consumers, verify strict declarations and runtime dependency resolution, and reject browser imports. Browser/gallery watch does not watch Node source; run `yarn build` after Node edits.

### Node content security policy

`@hmcts/rpx-xui-core-lib/node/server/security` provides `csp`, `getContentSecurityPolicy`, `SECURITY_POLICY` and `CspOptions` from Node Lib source `722b6284da957dbf4eebde0b49d36574d9664e3e`. Importing this entry requires the optional `helmet@^8.1.0` peer at runtime. Peer metadata applies to the whole package: a consumer already providing Helmet must satisfy this range even when it imports another entry. Runtime isolation does not isolate package-manager peer constraints. The maintained package gate tests Helmet 8.1.0, 8.2.0 and 8.3.0 with strict declarations, the three frozen app configuration shapes, local HTTP, browser enforcement and dependency audits. The development/main installed fixture and inspected app locks select 8.3.0. The range replaces the legacy library's incompatible Helmet 7 peer declaration; future releases and real app adoption still require validation. Other Node and browser entries do not import Helmet. For logger-only consumers, import `getLogger` and `XuiLogger` from `/node/server/logging`: installed runtime and bundle guards keep authentication, sessions, security and their dependencies out of that entry. The broader `/node/server` convenience entry exposes the same logger implementation.

The middleware keeps the source policy values, per-request nonce, environment/default/explicit-empty-array behavior, array concatenation order and duplicates. `CSP_REPORT_ONLY` still takes effect per request and generated `useDefaults`/`reportOnly` values retain their precedence over the supplied default policy. The injected `getContentSecurityPolicy` helper receives the existing policy object by reference. The broad non-nullish `defaultCsp` option remains accepted; Helmet validates recognized runtime fields.

Three differences are intentional and covered by tests: the CSP-specific merge preserves valid custom iterable directive values instead of the old generic merger corrupting them; it snapshots own root options and directive values once per request when combining generated arrays, so inherited policy values cannot shadow nonce-bearing directives; and an own `__proto__` directive reaches Helmet's invalid-name rejection instead of being silently discarded. It does not reject the valid directive-name tokens `constructor` or `prototype`. There is no runtime deepmerge/fork dependency. These changes do not tighten the allow lists, normalize source strings, remove duplicates or change the existing style-attribute policy. The full gate covers native HTTP headers, real browser enforcement/report-only behavior, packed app option shapes and controlled nonce/header/merge faults. The frozen app fixtures redirect imports and configuration to synthetic local values; they do not establish whole-application cutover or deployment acceptance.

The local HTTP session checks exercise the real Express/express-session middleware with an in-memory store: signed-cookie reuse, fresh and tampered-cookie isolation, uninitialized-session behavior, expiry/HttpOnly/secure flags, and a store error reaching the application handler before the protected route. Controlled wrong-cookie, wrong-store and save-uninitialized faults fail those checks and restoration passes. This proves the middleware contract with that store; it does not establish Redis protocol, deployed TLS or proxy configuration acceptance.

For values that must remain literal, pass a separate literal map as the third argument to `getTranslationWithReplacements$`, for example `service.getTranslationWithReplacements$('Hello %NAME%', {}, { NAME: name })`. In templates use `phrase | rpxTranslate: null: undefined: { NAME: name }`. Literal values are inserted without translation or translation-cache storage and retain their exact whitespace. Callers must still avoid passing personal data as the phrase itself or as a translatable replacement; changing this API does not automatically migrate existing consumers.

`yarn test:cache-upgrade` first rejects a controlled baseline source mismatch, then checks sequential cache reuse between published legacy translation, a historical Dexie 4.4.4 core baseline and the installed Dexie 4.4.7 candidate. Reports and the package/source-map receipt are under `test-results/cache-upgrade-*`. This does not establish simultaneous provider identity, deployed application behaviour or release compatibility.

Translation input is a data boundary: send only approved static UI text to the configured service. Existing string replacements are themselves translated; do not assume they stay local. User and case values passed directly as phrases can also reach HTTP and persistent IndexedDB. Consumer owners must classify these values, choose an approved endpoint and decide cache lifetime before adoption. Browser storage is an optional cache, not confidential storage. Validated malformed responses fall back without caching; storage failures preserve usable output and log only fixed failure categories.

## Architecture contract

One installed package must not become one eagerly loaded application bundle. The planned package uses real capability entry points, with no root aggregate module. Small startup/UI/validation consumers must not retain the case renderer or Node implementation. Applications own route-level dynamic loading; entry points alone do not make imports lazy. Installing one package still installs its declared dependency set.

Candidate boundaries include session support, case configuration, validation, focused UI capabilities, case lists, the coupled case renderer, translation and Node services. Names and granularity remain subject to real dependency graphs and packed-output evidence. Do not add placeholder public APIs to reserve them.

Before bulk migration:

1. Confirm supported consumers, framework versions and the complete dependency contract.
2. Prove browser/server isolation and declaration resolution using the actual packed artifact, including the Node CommonJS marker.
3. Prove canonical translation ownership and the legacy facade with compatible external Media Viewer/payment releases and a representative case path.
4. Measure small-consumer, startup-versus-renderer and list-only loading with the consumers' real builders.

Broader supported Angular cohorts and the complete future manifest remain design/compatibility gates. This foundation proves only its concrete initial APF dependency graph; publishing credentials and release automation remain absent. Package release must eventually publish the exact tested tarball without rebuilding it.

The exact `minimatch@11.0.8` and `glob@14.0.6` descriptors are preapproved for security fixes; Yarn's default age gate remains active for every other package version.

Repository administrators must verify real clean, failing and fork workflow behaviour before making additional contexts required. Secret scanning, push protection, alert routing and bypass review are repository/organisation settings and need their own read-back evidence; this workflow does not enable them. Preserve existing approvals and required checks.

For every candidate, retain source/run identity, native results, the tested tarball and digest, the dependency report and independent review. The EXUI code owners review engineering changes; name a security champion for weekly alert/update triage and monthly access, exception, toolchain and compatibility reviews. Library package publication remains disabled. Before adoption, consumer and release owners must accept real app builds/journeys, supported dependency cohorts, input/privacy and accessibility behaviour, an SBOM/licence review, retained evidence and a rollback rehearsal.
